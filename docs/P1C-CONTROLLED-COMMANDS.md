# ORBI LIVING — P1C Controlled Operations Commands

## Goal
Move operational writes behind server-controlled commands while preserving Supabase RLS as a second authorization layer. The client never chooses actor identity or community scope.

## Commands in this cut

### Shift management
`POST /api/operations/shifts/command`
- requires `manage_shift_schedule`;
- administrator/mayordomo only under the current permission matrix;
- validates UUID, expected revision, target state and assignee;
- filters the database update by `community_id` and `revision`;
- returns `409` on stale revision or invalid transition.

### Report shift gap
`POST /api/operations/shifts/report-gap`
- requires `report_shift_gap`;
- permits concierge/mayordomo/administrator according to the matrix;
- moves an eligible shift to `vacant` and clears the effective assignee;
- database trigger restricts concierge mutations so they cannot alter the shift definition or perform arbitrary state changes.

### Receive handoff
`POST /api/operations/shifts/handoff`
- requires `confirm_shift_handoff`;
- only accepts a `confirmed` shift with an assignee;
- transitions to `received` with optimistic revision checking.

### Report incident
`POST /api/operations/incidents/report`
- requires `report_incident`;
- community, actor, state and timestamps are server controlled;
- accepts only structured area/priority and an optional short case reference, not a free-text public narrative.

### Manage incident
`POST /api/operations/incidents/command`
- requires `manage_incident`;
- supports valid state transition, priority change and role assignment;
- uses expected revision to reject stale writes.

## Database enforcement
The P1C migration adds:
- a check requiring an assignee for `confirmed`/`received` shifts;
- shift transition validation in PostgreSQL;
- incident transition validation in PostgreSQL;
- tightly scoped concierge shift updates for `vacant` reporting and `received` handoff only;
- append-only `shift_events` generated by database trigger;
- append-only `incident_events` generated by database trigger;
- direct authenticated INSERT into event tables remains denied.

Application validation and database validation intentionally overlap. UI/server validation gives useful errors; database enforcement protects against bypass or future regressions.

## Concurrency model
Every mutation carries `expectedRevision`. The REST update is filtered by the current revision. If another operator wins the race first, zero rows are returned and the API responds `409 Conflict` rather than silently overwriting the newer state.

The existing revision trigger increments the row after an accepted update and server timestamps remain authoritative.

## Privacy boundary
No PII is added by P1C. Real staff IDs remain private references. Incident reporting in this cut deliberately avoids free-text narratives, photos, phones, plates, RUT or resident information.

## Acceptance gate
P1C is not Ready until:
1. `npm run check` is GREEN;
2. migration applies cleanly to staging;
3. valid and invalid shift transitions are tested under real RLS roles;
4. concierge can report a gap and receive a confirmed handoff but cannot perform broader shift edits;
5. domain events are automatically appended with the authenticated actor;
6. invalid incident transitions are rejected in PostgreSQL;
7. stale revision updates are demonstrated to affect zero rows / return conflict at API level once end-to-end Auth is available;
8. Supabase Security Advisor is reviewed after DDL changes.
